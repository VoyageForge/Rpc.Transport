# Rpc.Transport 通讯架构

## 1. 包的边界

`Rpc.Transport` 是一个独立的 Unity UPM Package，包名为 `com.voyageforge.rpc-transport`，程序集为 `VoyageForge.Rpc.Transport`。它只负责“请求和响应如何被承载、编码、发送与接收”，不负责服务查找、参数绑定或调用业务方法。

```text
业务 Host / Unity 游戏
        │
        ├── Rpc.Executor ── 服务注册 / 方法解析 / 参数绑定 / 业务调用
        │        │
        │        └── 依赖 Rpc.Transport
        │
        └── Rpc.Transport ── 消息模型 / Serializer / Client / Server
                 │
                 ├── TCP Client / TCP Server
                 ├── 未来：UDP / WebSocket / Named Pipe
                 └── 由 Host 选择 Serializer 实现
```

依赖方向固定为：`Rpc.Executor -> Rpc.Transport`。`Rpc.Transport` 不得引用 `Rpc.Executor`，因此通讯包可以独立用于心跳、设备发现或其他消息协议，也可以被其他 RPC 执行内核复用。

## 2. 为什么消息模型放在通讯包

`RpcRequest`、`RpcResponse` 和 `RpcError` 是跨 Host、传输端和执行端传递的消息信封：

- `RpcRequest` 描述目标服务、方法、原始参数和请求头。
- `RpcResponse` 描述成功结果或结构化错误。
- `RpcError` 使用稳定的错误码，避免调用方解析提示文本。

这些类型不依赖某一个 Socket 或序列化协议，因此与 Transport 抽象放在同一个轻量 Runtime 程序集中。`Rpc.Executor` 的 `ExecuteAsync` 直接消费 `RpcRequest` 并返回 `RpcResponse`。

## 3. 核心接口

| 接口 | 方向 | 作用 |
|---|---|---|
| `IRpcClientTransport` | Client -> Server | `SendAsync` 发送请求并等待响应 |
| `IRpcServerTransport` | Server <- Client | 启停监听，并通过 `OnRequestAsync` 将请求交给 Host |
| `IRpcDatagramTransport` | 双向 | 组合 Client 与 Server 能力，供 UDP 等数据报通道使用 |
| `IRpcTransport` | 兼容 | 保留旧的无请求 Token 服务端事件 |
| `IRpcSerializer` | 编码/解码 | 把 `RpcRequest` / `RpcResponse` 与 `byte[]` 互转 |

客户端和服务端分开定义，是为了允许只实现单向能力。例如一个 WebSocket Client 不需要为了满足接口而暴露 Server Listener。`IRpcDatagramTransport` 只有在实现确实同时具备两种能力时才使用。

`IRpcServerTransport.OnRequestAsync` 的第二个参数是服务器请求生命周期 `CancellationToken`。服务端停止时可以取消正在运行的工作，并由 Host 传给 `RpcExecutor.ExecuteAsync`。TCP 服务端在业务执行期间没有继续读取连接，因此客户端中途断开不一定会立即被发现；这个 Token 不能被理解成可靠的远端断线通知。

## 4. Serializer 与安全

通讯包仅定义 `IRpcSerializer`，不绑定 JSON、MessagePack 或 Protobuf。TCP 实现只接收和发送序列化后的字节，不读取 JSON 字段。

项目应自行实现序列化器。若使用 JSON，应关闭类型元数据自动实例化能力（例如 Newtonsoft 的 `TypeNameHandling.None`），并为复杂 DTO 建立明确的类型白名单/转换规则。不要直接信任远端提供的 CLR 类型名称。

## 5. TCP 参考实现

源码位于 `Runtime/Scripts/Transports/Tcp`：

- `TcpRpcClientTransport`：每次请求建立一条连接，发送一帧请求、读取一帧响应后释放连接。
- `TcpRpcServerTransport`：后台 Accept 循环，每条连接由独立处理任务负责请求与响应。
- `TcpFrameProtocol`：4 字节 Big Endian 长度前缀 + Payload，循环读取直到完整帧，默认最大帧长度 1 MiB。

TCP 是字节流，不能依赖一次 `Write` 对应一次 `Read`。长度前缀用于恢复消息边界。协议拒绝零长度、超上限长度和未完整接收的帧。

当前实现是第一版可阅读的请求响应传输，不包含长连接复用、连接池、TLS、认证、自动重试或多路复用。生产环境必须结合威胁模型补齐认证、授权、限流、日志脱敏和超时策略。

## 6. UDP 扩展边界

本包目前定义 `IRpcDatagramTransport`，不提供 UDP Socket 实现。不要把 TCP 4 字节流分帧协议直接搬到 UDP。UDP 请求响应需要额外设计 RequestId、超时、丢包检测、重传、去重、最大数据报大小和分片策略。设备发现与心跳通常比可靠 RPC 更适合作为第一批 UDP 功能。

## 7. 测试

测试按“接口契约”与“真实网络集成”分层：

- `Tests/Editor` 使用内存替身验证 Client、Server、Datagram、旧版 `IRpcTransport`、Serializer 和响应模型契约。
- `Tests/Runtime/TransportContractsPlayModeTests.cs` 验证 Player Loop 下异步请求和生命周期 Token 转发。
- `Tests/Runtime/TcpRpcTransportPlayModeTests.cs` 使用 `127.0.0.1` 动态端口，验证真实 TCP 连接、并发客户端、对端断开、截断帧、非法/超长帧、反序列化失败、响应序列化失败、Handler 异常、空响应、无 Handler、连接拒绝、客户端取消和服务端停止。
- `Rpc.Executor/Samples~/Tcp/Tests/Runtime` 另外使用真实 NewtonsoftRpcSerializer 对大体积 Unicode/Emoji 字符串进行并发 TCP 往返，记录字节数、耗时与吞吐量。

测试代码通过公开通讯接口和 TCP Client/Server 完成真实功能验证，不引用 RPC/Console Source Generator，也不引用 `RpcGeneratedDispatcher` 或 Console Builder 等生成类型。Source Generator 作为独立 Analyzer 项目由各自构建脚本正常编译；Unity 在编译用户契约代码时按标准编译流程运行生成器。

若本包通过 Local/Git/Registry 外部依赖安装，要发现包内测试，请在项目 `Packages/manifest.json` 的 `testables` 数组中加入 `com.voyageforge.rpc-transport`。若本包直接放在项目 `Packages/` 下作为 Embedded Package，则无需此项配置。之后在 Test Runner 中分别运行 EditMode 和 PlayMode 测试。
