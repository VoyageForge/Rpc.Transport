# Rpc.Transport 源码阅读指南

本文按“先抽象、再实现、最后验证”的顺序组织，适合第一次阅读网络通讯代码。

## 1. 推荐顺序

1. `Runtime/Scripts/Abstractions/RpcMessages.cs`：先看 Request/Response/Error 三个跨边界消息模型。
2. `Runtime/Scripts/Abstractions/TransportContracts.cs`：看 Serializer、Client、Server 和 Datagram 接口。
3. `Runtime/Scripts/Transports/Tcp/TcpFrameProtocol.cs`：理解 TCP 字节流为什么需要长度前缀。
4. `Runtime/Scripts/Transports/Tcp/TcpRpcClientTransport.cs`：理解一次请求如何建立连接、写帧、读响应。
5. `Runtime/Scripts/Transports/Tcp/TcpRpcServerTransport.cs`：理解 Accept 循环、连接处理、回调与停止过程。
6. `Tests/Editor/TransportContractsEditModeTests.cs`：理解接口在普通异步上下文中的契约。
7. `Tests/Runtime/TransportContractsPlayModeTests.cs`：理解 Unity Play Mode 下的异步执行和取消令牌传播。

## 2. 从 RpcRequest 开始

`RpcRequest` 只表达调用意图：`ServiceName`、`MethodName`、`Parameters` 和 `Headers`。它不知道 IP、端口或 Socket。`RpcResponse` 的 `Success` 决定结果该从 `Result` 还是 `Error` 读取。

注意：`Parameters` 是 `object[]`，网络层反序列化出的数字可能仍是 JSON token 或其他中间对象。最终参数转换由 `Rpc.Executor` 负责，而不是通讯层负责。

## 3. 接口如何分工

`IRpcClientTransport.SendAsync` 是客户端统一入口；`IRpcServerTransport` 管理监听生命周期并通过事件把请求交给 Host。Server 不依赖 `RpcExecutor`，事件订阅者可以是执行器、消息路由器或测试服务。

`IRpcDatagramTransport` 继承 Client 和 Server 接口。它只是能力组合，不会使 UDP 自动可靠。`IRpcSerializer` 则是独立的编码策略。

## 4. TCP 帧协议

TCP 不保留应用层消息边界。即使发送端一次 `Write` 一个 JSON，也可能被接收端拆成多次 `Read`；多个写入也可能在接收端一次读到。因此帧协议用 4 字节大端长度表示 Payload 大小。

读帧有两个必须分清的场景：

- 新帧开始前读到 EOF：表示对端正常关闭，没有更多消息。
- 长度头或 Payload 读取一半后 EOF：表示帧被截断，必须报错。

`ReadExactlyAsync` 通过循环累计已读字节数，不假设一次读取能满足请求长度。

## 5. 服务端生命周期

`StartAsync` 启动 Listener 并启动后台 Accept；每个客户端连接进入独立的 `HandleClientAsync`。`StopAsync` 取消生命周期 Token、停止 Listener、关闭活动连接并等待 Accept 循环退出。

`OnRequestAsync` 允许 Host 把服务端 Token 传入业务调用。TCP 对端在 Handler 运行时断开连接不一定能被立即检测，所以不要把它用作客户端取消的确认机制。

## 6. 测试为什么使用内存传输

接口层测试的重点是调用约定，而不是操作系统 Socket：传入的请求是否原样传递、取消令牌是否原样传递、响应是否被返回、Client/Server 能力是否组合正确。内存实现能让 EditMode 和 PlayMode 测试快速且稳定地验证这些约定。
